# audio/ui

**audio/ui** is an open-source library of accessible, composable Audio UI components for React: headless primitives and a shadcn registry of styled components built on them, all copied from the registry, designed to be copied, pasted, and owned.

- Site: https://www.audio-ui.dev · Repo: https://github.com/ouestlabs/audio-ui
- Registry endpoint: `https://www.audio-ui.dev/r/{style}/{name}.json`
- Domain language (Parameter, Commit, Primitive, Element, TransportClock…): [CONTEXT.md](CONTEXT.md). Use these words in code, docs and replies.
- Contribution guide with the full registry walkthrough: [CONTRIBUTING.md](CONTRIBUTING.md)

This file is the single source of instructions for every coding agent (Claude Code loads it through `.claude/CLAUDE.md`; Codex, Cursor, Copilot, Gemini, Zed and others read it directly).

## Monorepo

Turborepo + Bun workspaces. **Always use `bun` / `bunx`, never `npm`, `npx` or `pnpm`.**

The apps share their dependency versions through the Bun catalog in the root `package.json` (`workspaces.catalog`): an app depends on `"react": "catalog:"`, and a version is changed once, there. The published packages keep explicit versions and peer ranges.

```
audio-ui/
├── apps/
│   ├── www/        # TanStack Start docs site + registry (Fumadocs + MDX, prerendered, Cloudflare) → localhost:4000
│   └── video/      # Remotion videos of the real components (see apps/video/README.md)
├── packages/
│   └── icons/      # @audio-ui/icons, published: audio glyphs (one thin stroke on a 24 grid, in four weights)
└── skills/         # The agent skills we ship to library users: audio-ui, web-audio, design (npx skills add ouestlabs/audio-ui)
```

## Commands

```sh
bun run dev             # Start all apps
bun run build:pkg       # Build the published package (icons)
bun run lint:fix        # Auto-fix with Biome
bun run changeset       # Describe a change to a published package
```

From `apps/www/`:

```sh
bun run registry:build  # Regenerate registry JSON + site manifests, after any registry change
bun run icons:build     # Regenerate icon mappings, after adding icons
bun run typecheck
bun test
```

## Where things live

### The engine (`apps/www/src/registry/lib/engine/`)

- `device/` (descriptions, engine contracts, worklet stages, feeds, noise, measuring an engine), `time/`, `analysis/` (levels, curves, peaks, loudness, pitch, beat and chroma), `midi/`, `pitch/` (scales, keys, note frequencies), `files/` (audio, MIDI and MusicXML files), `playback/`, `worklet/`: one module each, a registry item `engine-<module>` (listed in `registry/bases/modules.ts`, checked by `test/lib-modules.test.ts`) that installs to `lib/engine/<module>/`. The registry's files import a module as `@/engine/<module>` (a tsconfig path); the build rewrites it to `@/lib/engine/<module>` and adds the item. Its own files import each other by relative path, with no extension, and never an app alias (`imports.test.ts`)
- It is the one place that imports `@audio/*` atoms, so the registry builds on it rather than on the atoms. Its tests run with `bun test` in `apps/www`
- `playback/worklet-source.ts` and `loader-worker-source.ts` are generated by `bun run engine:worklet` in `apps/www`; a test fails when their sources changed without a rebuild

### The primitives (`apps/www/src/registry/primitives/`)

- Envelope, Fader, Knob, Meter, Pad, Piano, PianoRoll, Plot, Sequencer, Timeline, Waveform, XYPad: no package, files of the registry that the CLI copies into a project. `<name>/<name>.ts` is the primitive written by hand over `primitive.ts` (what every primitive shares), with only `@ui-sdk/*` as dependencies; beside it, the adapters (React, Vue, Svelte, custom elements) in `<name>/<framework>/`
- A file imports a primitive as `@/primitives/<name>` (a tsconfig path, never installed): the registry build rewrites it to the path the file lands at. Import a primitive by a relative path or by that alias, never as `@/components/audio-ui/<name>/<name>`: the shadcn CLI shortens it to the file itself
- A file shared by several primitives (`primitive.ts`, `grid.ts`, `frame.ts`, `pitch.ts`…) only gains exports once released, since the CLI keeps the copy a project already holds: `test/shared-files.test.ts` fails when one loses an export

### `apps/www/src/registry/`: one registry tree

`registry/` holds the design system (`styles/`, `icons/`, `fonts.ts`, `themes.ts`, `config.ts`: started as a fork of shadcn/ui, now audio/ui's own, so edit it freely) and, in `bases/`, everything the registry publishes, **the contribution surface**.

A shadcn **base** is a complete set over one behavior library, and a user picks one: `bases/base/` is the Base UI base, `bases/ui-sdk/` the ui-sdk base (its styles are `ui-sdk-<style>`). Never use one base's library in the other. Code that names no behavior library (the primitives, which only use `@ui-sdk/core`'s kernel, the engine, devices, hooks, libs, audio elements and blocks) is written once, in `bases/shared/`, and every base serves it as it is. A base's folder holds only what names its library: its `ui/` (shadcn's components written over its library, by the same names in each base: `bases/base/ui/` and `bases/ui-sdk/ui/`; a base answers the `@shadcn/<name>` an item names with its own, and leaves to shadcn the ones it has none of) and its variant of each item whose files name a library (`rocker-switch`, `parameter-field`), by the same name and path in each base, listed in its `audio-ui/_registry.ts`. A file imports a ui component as `@/components/ui/<name>` and such a variant as `@/components/audio-ui/<name>`, where they install, never from a base's folder: the site and the videos resolve both to the ui-sdk files (tsconfig paths and the vite alias). The installed paths do not depend on the folder. In this repo the site is built on ui-sdk, so `components/ui/` is written from `ui-sdk-nova` by `bun run ui:sync`, after `registry:build`. The style hooks of the ui components are `styles/style-<style>.css`, those of the audio components `styles/audio/style-<style>.css`.

```
registry/bases/shared/
├── audio-ui/elements/  # Styled elements over each primitive (knob.tsx, fader.tsx, timeline.tsx…)
├── audio-ui/panels/    # Panels that are no device's own: clip, rack, drum rack, the generic device-panel
├── devices/<name>/  # A device, named as it installs: device.ts, engine.ts, panel.tsx
├── components/      # Catalog by category folder: block-{component}-{variant}.tsx + {component}-*-demo.tsx
└── hooks/           # use-web-audio, use-transport-clock, use-spectrum…

registry/primitives/ # at the registry root, served by every base: the twelve primitives and their adapters
registry/lib/        # at the registry root, served by every base: engine/ and webgl/ (modules), then arrangement/, drums/, devices/, notes/, input/, demo/ (by use, `LIB_GROUPS` in `bases/items.ts`) and web-audio, zip, sortable-drag at the root; a lib installs to `lib/<name>.ts` whichever folder it is written in
```

Each of `audio-ui/`, `devices/`, `components/`, `hooks/`, `lib/`, `primitives/` has an `_registry.ts`: **update the matching one when adding anything**. File paths inside are relative to `bases/shared/`, except those of `lib/` and `primitives/`, which start at `registry/` (`lib/web-audio.ts`). Items are declared through the factories of `registry/bases/items.ts` (`libItem`, `hookItem`, `deviceItems`), which write a file's path, target and type and a device's four items from one description. A device's folder mirrors where it installs (`components/audio-ui/devices/<name>/`), each file with its `target`. The audio.js a device runs is the engine's: its worklet's kernels come from `@/lib/engine/kernels` (listed in `apps/www/scripts/engine/kernels.ts`, written by `bun run engine:kernels` there, checked by its `kernels.test.ts`) and the processors its description uses from `@/lib/engine/dsp`; a registry file never imports an `@audio/*` atom.

Shared audio glue has one home each. Use it rather than writing a copy into a block or an engine:

| Concern | Module |
| --- | --- |
| The page's `AudioContext`, and resuming it in the gesture that starts sound | `lib/web-audio` (`webAudio.getContext()`, `webAudio.resume()`); engines and libs take `ctx` instead, a hook given a node uses its context |
| A screen's output: one gain and a safety limiter | `hooks/use-master-bus` |
| Loading a worklet's source into a context, once per context | `@/lib/engine/worklet` (`loadWorklet`) |
| What an engine is and is made of: its contract, a worklet stage, a feed, noise | `@/lib/engine/device` |
| Anything an audio.js atom does (a decoder, an encoder, loudness, a pitch or a key, MIDI files) | the engine's modules (`@/engine/<module>`), never the atom imported in the registry |
| Chords on an instrument whose engine plays one voice | `hooks/use-polyphony` over `lib/polyphony`; `lib/voice-pool` for a device of the library |
| Every device with its engine, by stable id | `lib/device-library` |
| Steps and the playhead on the audio clock | `hooks/use-transport-clock` over `@/lib/engine/time` |
| Editing an arrangement, with undo | `lib/arrangement-state` (`apply(state, command)`), `hooks/use-arrangement` |

State that changes over time keeps one source of truth: an engine object or a pure reducer, with React state only mirroring what the screen shows. Values that move every frame (playheads, meters, spectra) go through a source (`createSource`), never `setState`. An engine that loads a worklet exposes `ready` and checks it was not disposed before it builds on the load.

`registry/bases/{components,registry,seo}.json` are **generated** by `registry:build` from the `_registry.ts` files and `registry/bases/categories.ts`: never edit them by hand. A new category goes in `categories.ts`; a category with zero items fails the build. Item tags not listed there (`ui`, `grid`) are free-form search tags.

### The site's own code (`apps/www/src/components/`, `lib/`)

Grouped by what it does for the reader of the docs, two levels deep, so no folder holds a long flat list:

- `components/site/`: the chrome (`layout`, `navigation`, `home`, `pages`, `providers`). `docs/`: the docs page and what its MDX renders (`page`, `mdx`). `preview/`: what shows a component (`component`, `frame`, `controls`). `code/`: what shows its code (`source`, `block`, `copy`). `customizer/`: the design-system customizer.
- `components/ui/` is the shadcn UI, left as it comes from shadcn and synced from it: never move or reorganize it, and keep the site's own components out of it. `icon-placeholder.tsx` stays at the root of `components/`: its path is the contract with the shadcn CLI.
- `lib/` follows the same idea: `docs/` (`content`, `menu`), `registry/` (`core`, `catalog`, the lookup of the registry's items), `agents/` (MCP, llms), `seo/`, `code/`, `design-system/`.

### Docs (`apps/www/src/content/docs/`)

MDX under `(root)/` (the Get started guides) and `components/base/`. Use the existing components (`<ComponentPreview>`, `<ComponentSource>`, `<Install>`, `<Steps>`), not raw HTML. A component page's Installation section is one `<Install name="knob" packages="@audio-ui/react class-variance-authority" />` (or `kind="device"` for a device, whose Panel section shows `<DeviceUsage name="<slug>" />`), drawn from `lib/docs/content/install-docs.ts`; only a page whose installation differs, such as the timeline's, writes its own `<CodeTabs>`.

The docs, `categoryGroups` and the shipped skill share one map, by what the reader builds. Each space is a folder of `components/base/` (the parentheses keep it out of the URL, so a page stays `/docs/components/base/<name>`), with its sections in its `meta.json`:

- `(elements)/`: the pieces of any audio interface. Controls, keyboards and pads, displays.
- `(workstation)/`: the surfaces of a DAW. Arrangement, editors, the piano roll's tools, transport and mixing.
- `(devices)/`: effects and instruments, like plugins. One page per device, by family.
- `guides/` (beside `components/`, at `/docs/guides/<page>`): guides to what makes the sound, a page per concept (output, clock and time, synthesis, input, analysis), each linking to the hook and lib entries it uses. Its overview says how an engine of the user's own drives the components.

The docs are in sections (`lib/docs/content/sections.ts`), switched at the top of the sidebar, with the reader's framework (React, Vue, Svelte or Web, `lib/docs/content/frameworks.ts`) chosen under it: **Docs** (`(root)/`, `guides/`, `hooks/`, `lib/`, `engine/` and `gl/`: what makes the sound sits beside the guides that use it); **Components** (`components/`, whose pages of the twelve primitives (`PRIMITIVE_PAGES` in `framework-paths.ts`) are every framework's, and `(overview)/` for the devices' overview page); **Icons** (`icons/`, the usage page, and the icons' catalog at `/icons`, whose side panel holds the icon picked, its weight and its size). The framework chosen (React by default) names the hero and opens the tabs of `<FrameworkTabs>` on its own. It is kept in the browser, and every page of the docs it is shown has an address for it, `/docs/<framework>/<page>` (`lib/docs/content/framework-paths.ts`: `/docs/vue/engine/analysis`, `/docs/web-components/components/base/knob`, with `web-components` for Web), which the router rewrites to the page's own address; a link or a page loaded whole goes to the address of the framework kept. The pages only a React app uses (the catalog, guides, hooks, libs, styling and API) have none for the others. A folder in parentheses adds no URL segment, so a component page stays at `/docs/components/base/<name>`.

Every hook and lib has its own entry page, `hooks/<name>.mdx` or `lib/<name>.mdx`, listed once in that folder's `meta.json`. It opens with `<Entry name="<name>" />`, which draws the install command, the import, the files, what it depends on, what uses it and its exports from `lib/docs/content/entries.generated.json` (written by `registry:build` from the `_registry.ts` files and the sources), then goes on with a written Usage section. `test/registry-entries-docs.test.ts` fails on an entry with no page or a page with no entry.

Every module of the engine and of webgl has a page the same way: `engine/<module>.mdx` or `webgl/<module>.mdx`, headed by `<Module from="@/lib/engine/<module>" />` or `<Module from="@/lib/webgl/<module>" />` (the install, the import, the hooks and libs that use it, the audio.js packages it builds on, each linked to its page on audio.js.org, and its exports), read from `lib/docs/content/package-modules.generated.json`, which the same `registry:build` writes from the packages' exports and sources. `test/package-modules-docs.test.ts` fails on a module with no page.

How items are grouped:

- One item is something a user installs for itself. Split only where a piece is useful without the rest; code that only one piece uses ships in that piece's item (an item can hold several files).
- A component page is a component a user puts on screen. A hook or a lib is documented on its own entry page; the component page that uses it says what it does in a sentence and links to it.
- Workstation and Devices parts are controlled and engine-agnostic: state comes in as values and live sources, changes go out through callbacks, never through one of our audio hooks. They must work over an engine of the user's own (an AudioWorklet, WASM).

A primitive has one page: the component's (`components/base/(elements|workstation)/<name>.mdx`, the timeline's is `arrangement.mdx`). Its styled React component is inside `<ForFrameworks only="react">`, and its **Headless primitive** section, for every framework, holds the install of each adapter, its usage, options and what a change reports. Its API reference ends with the parts, the tags of the web adapter and the events as each framework names them, drawn by `<PrimitiveParts>`, `<PrimitiveTags>` and `<PrimitiveEvents>` from `lib/docs/content/primitive-api.generated.json`, which `registry:build` writes from the primitive's source and its adapters: `test/primitive-api.test.ts` fails when it is stale, when an option of the source is in no table of the page, or when the three adapters export different parts.

## Rules

### Registry items (`registry/bases/shared/components/{category}/<framework>/`)

- Filename `block-{component}-{variant}.tsx` (blocks) or `{component}-{feature}-demo.tsx` (demos); default export `Block{Component}{Variant}` / `{Component}{Feature}Demo`, PascalCase of the filename, no params
- No `"use client"` directive: the site is TanStack Start, where it means nothing
- Icons via `IconPlaceholder` (`@/components/icon-placeholder`) with a name for all five libraries (`lucide`, `phosphor`, `tabler`, `hugeicons`, `remixicon`), sized with `className="size-4"`, never a numeric `size`
- Each icon name is a string literal: the shadcn CLI turns `IconPlaceholder` into an import, so `lucide={playing ? "PauseIcon" : "PlayIcon"}` installs as invalid code. Render one element per icon (`{playing ? <IconPlaceholder … /> : <IconPlaceholder … />}`); `apps/www/test/install-paths.test.ts` fails on an expression
- Icon-only interactive elements get `aria-label`; decorative icons get `aria-hidden="true"`
- Static data outside the component function
- Semantic color tokens only (`text-muted-foreground`, `bg-primary`), never raw palette colors; don't add `border-border`, it's the default
- React imports are named, never `import * as React`
- `registryDependencies`: audio/ui items as `"@audio-ui/{name}"`, shadcn as `"@shadcn/{name}"`; npm imports go in `dependencies`
- Installed components land in `components/audio-ui/<file>.tsx` (hooks in `hooks/`, libs in `lib/`, blocks in `components/examples/`), so docs and the skill import them as `@/components/audio-ui/<name>`. `apps/www/test/install-paths.test.ts` fails on an import the registry doesn't install

### Published packages

- Relative imports carry the `.ts` extension (`./x.ts`, compiled with `rewriteRelativeImportExtensions`). A `.js` specifier breaks the www Turbopack build.
- Every user-visible change to `packages/icons` needs a changeset (`bun run changeset`). Never edit `package.json` versions.
- The web adapters are served as scripts by version (`apps/www/public/web/<version>/`, the version in `apps/www/src/registry/web-version.json`), and the files of a version never change for the people pinned to it. A change to an adapter of `primitives/*/web/` or to what it builds on raises that version, so the next build writes a new folder; commit the folder `registry:build` writes, and never edit an older one.

### Writing (docs, changesets, comments, commit messages, UI copy)

- No em dashes. Use a comma, a colon or a period.
- Describe audio/ui's own API. Don't name the underlying headless library (Base UI) or the DAWs a feature is modeled on; only the peer dependency and imports name Base UI.
- Quote an MDX frontmatter `description:` that contains `": "`, or every docs page 500s.

### Before you call it done

1. `bun run lint:fix` (Biome via Ultracite: it enforces most style rules, so run it rather than memorising them)
2. After a registry change: `bun run registry:build` from `apps/www/`, **after** the last lint fix, so the generated JSON matches the formatted source
3. The checks CI runs on every PR:
   ```sh
   bunx biome ci packages/icons apps/www/src/registry/lib/engine apps/www/src/registry/lib/webgl
   bun run build:pkg
   (cd packages/icons && bunx tsc --noEmit && bun test)
   ```
   For `apps/www`: `bun run typecheck` and `bun test`.
   For the primitives: `bun run test:primitives` in `apps/www`, which drives the same scenarios against the adapters of React, Vue, Svelte and custom elements in `registry/primitives/`. It runs apart from `bun test` because Svelte needs its browser build.
4. For UI changes, look at the page in a browser (dev server on :4000) and tab through the controls.

## Workflow skills

Step-by-step guides for the recurring jobs live in `.claude/skills/` (mirrored at `.agents/skills/` for agents that read that path). Read the matching `SKILL.md` before starting:

- `add-registry-item`: add or change a block, demo, element, hook or lib in the registry
- `change-primitive`: change a primitive, its adapters, or the audio logic of a published package
- `film-component`: render a component's video with `apps/video`

`skills/` is different: it holds the three skills we **ship** to people using the library (`audio-ui`, `web-audio`, `design`, one Claude Code plugin), not guides for working on this repo. One rule per file in each skill's `rules/`, compiled into its `AGENTS.md` by `bun run skill:build` (from `apps/www`); the [README](skills/audio-ui/README.md) explains how to add a rule. `apps/www/test/skills.test.ts` (run in CI) fails on a malformed rule, a stale `AGENTS.md`, or a registry item, entry, data attribute or CSS variable that doesn't exist: when you rename one, update the skill in the same commit.

## Working guidelines

These bias toward caution over speed. For trivial tasks, use judgment.

**Think before coding.** State your assumptions. If several interpretations exist, present them instead of picking silently. If a simpler approach exists, say so. If something is unclear, stop and ask.

**Simplicity first.** The minimum code that solves the problem: no speculative features, no abstraction for single-use code, no configurability nobody asked for, no error handling for impossible cases. If 200 lines could be 50, rewrite it.

**Surgical changes.** Touch only what the task needs. Match the existing style. Don't refactor or reformat adjacent code; mention unrelated dead code instead of deleting it. Do remove the imports and helpers your own change orphaned.

**Goal-driven execution.** Turn the task into checks you can run ("fix the bug" → a test that reproduces it, then passes), state a short plan with a check per step, and loop until the checks pass.
